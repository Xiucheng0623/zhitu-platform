## 二、本轮发现并修掉的 5 个真实缺陷

### 1. webhook 被 SSRF 防护静默丢弃（P0 级，已修防护 + 已加断言）

现象：`check_webhook_push.py` 输出「20 秒内平台未更新」，但脚本没有断言，
退出码 0 被判成 PASS —— **假绿**。

根因：LS 1.23 的 SSRF 防护默认禁私网，本机 LS 重启时漏了
`USE_DEFAULT_BANNED_SUBNETS=false`，日志里每秒一条
`URL resolves to a reserved network address (block: 127.0.0.0/8)`。

修复：
- 本机 LS 带正确变量重启；实测造标注 **1 秒内 +1、删除 1 秒内回退、无 SSRF 拦截**；
- `check_webhook_push.py` 改为带硬断言（造标注失败 / 20s 不变 / 不回退 / 日志有拦截 → 退出码 1）；
- `smoke.sh` 新增两条断言：LS 容器里该变量必须为 false；LS 容器必须能直连编排层 `/healthz`；
- `probe_package_health.py` 新增 compose 配置断言；
- `deploy/README.md` 补排障条目。

生产 compose 本来就有这个变量（`docker-compose.yml` 第 223–226 行），所以生产不是配置缺失；
但**原来的测试发现不了它**，这才是真正要修的地方。

### 2. 已标注任务的「逐条打开」会跳到下一条（数据一致性承诺被破坏）

现象：平台「我的数据」第 1 行是 LS task #5（已标注），点「打开这一条」，
URL 是 `?labeling=1&task=5`，但 LS 渲染出来的是 **#6 / 第 2/2 条「样本 B」**。

根因（浏览器实测 6 种 URL 得出）：LS 标注流队列**只排未标注任务**，
`labeling=1&task=<已标注id>` 会被静默跳到下一条。
不带 `labeling=1` 的 `/projects/13/data?task=5` 能精确选中 #5 并显示已有标注结果。

修复：
- `assignment.py`：`open_path` 按 `is_labeled` 分流；
- `ls_bridge.py`：签票据前已读 `remote_task`，同样按状态分流落地地址；
- `Tasks.tsx`：已标注行按钮改为「查看这一条」，不再假装能进标注流；
- 验证脚本同时覆盖两种状态（已标注 → 数据管理视图；未标注 → 标注流且 `task` 精确）；
- `README.md` / `check_package.py` 同步。

复验：`verify_annotator_data_ui.py` **22 项全绿**；`verify_annotator_data_parity.py` 全绿。

### 3. webhook 复用时只比对事件、不校验验签头（已修）

现象：`ensure_webhook()` 复用的判定条件只有「url 相同 + actions 相同」。
`LS_WEBHOOK_SECRET` 为空时建的 webhook 里没有 `X-Forge-Secret` 头；后来平台
配上了 secret，回调会被 handler 按 **404** 丢掉（不泄露端点存在），而这个函数
仍然返回 `{"reused": true}` —— **和 SSRF 拦截完全一样的失败模式**：数字不动，
但自检全绿。

修复（`clients.py`）：
- 复用前同时核对 `headers`，缺 `X-Forge-Secret` 时 `PATCH` 补齐；
- 反向也要收敛：平台把 secret 撤掉后，把 LS 侧残留的 `X-Forge-Secret` 删掉
  （功能上不致命，但等于把旧口令明文挂在 LS 的 webhook 配置里）；
- 返回值带 `headers_updated`，让调用方（和测试）能看出这次到底改了什么。

复验：`probe_webhook_secret.py` 7 项全绿（补齐场景）；探针 secret 清理后
`probe_webhook_cleanup.py` 7 项全绿（清除场景：`headers_updated=True`、
LS 侧 `headers={}`、无头回调仍 200）。

### 4. 备份存了 `.env`，恢复流程却从不使用（已修）

现象：`backup.sh` 确实把 `.env` 存成 `.env.bak`（权限 600），但 `restore.sh`
只用当前 `.env`，结尾一句「若来自另一台机器，注意核对密钥」了事。

影响：跨机恢复时 `LS_SSO_SECRET` / `LS_REFRESH_TOKEN` / `FORGE_JWT_SECRET`
对不上，结果是**库恢复了、服务也起来了，但平台读不到 LS 任务、甲方 SSO 进 LS 全 401**
—— 症状看起来像代码坏了。

修复（`restore.sh`）：
- 新增第 0 步「检查配置配套性」：逐项比对 9 个密钥类键，列出不一致项并说明典型症状；
- 有差异时默认**不**改 `.env`，但要求显式输入 `keep` 才继续（`yes` 会被拒）；
- 新增 `--env=backup`：把当前 `.env` 另存为 `.env.pre-restore-<时间戳>`（600），
  再换回备份版本；连库账号在建连前就读好，不因换配置而换成另一台机器的管理员名；
- 所有交互提示改用 `echo` 输出，重定向/CI 下日志里也能看出卡在哪一步。

复验：`probe_restore_env.py` **16 项全绿 + 1 项平台限制说明**
（本机 NTFS/msys 不保留 600 权限位，Linux 上 `chmod 600` 生效，不冒充缺陷）。

### 5. 回调端点先打 LS、后验证 project 归属（已修）

现象：`POST /api/v1/webhooks/labelstudio` 的原有顺序是「先 `project_summary()`
翻 LS 全量页（最多 100 页 × 100 行）→ 再查 `forge.tasks` 确认这个 project 是不是
平台绑定的」。而 `LS_WEBHOOK_SECRET` 为空时（内网联调就是这样）完全不验签。

后果：任何人构造一个**不存在的 project id** 连发几十条请求，就能让平台替他去压
LS（2000 行约 10 秒/次），同时把审计表刷满。这不是理论风险 —— 本轮做「无头回调
仍被接受」验证时顺手打了一条假 project，平台立刻返回 `{"synced": true}`。

修复（`main.py`）：
- 先查 `forge.tasks` 有没有这个 `ls_project_id`，**没有再打 LS**；
- 未绑定 project 返回 `{"ok": true, "ignored": "unknown_project"}`：给 200 是刻意的
  （避免 LS 反复重投），但不打 LS、不写审计、不落账；
- 启动时若未配 `LS_WEBHOOK_SECRET`，日志明确告警「回调端点无鉴权」，
  不再让「裸着跑」这件事只存在于读代码的人脑子里。

复验：`probe_webhook_guard.py` **10 项全绿** —— ghost project 响应 **15 ms**
（说明真没去翻 LS）、LS 日志无该 id 请求、审计无记录、已绑定 project 仍 `synced=true`。

## 三、模拟全量数据：真实数字（不是估算）

场景：临时 LS 项目 + 临时批次绑定张三，不碰 13/14 和现有批次，跑完即删。

| 档位 | 单次响应耗时（三轮实测） | 响应体 | 返回行数 | 截断 | 结论 |
|---|---|---|---|---|---|
| 500 行（合同量级） | 2.95 – 3.22 s | 558 KiB | 504（含原有 4 行） | 否 | 可用 |
| 2000 行（上限） | 9.99 – 10.29 s | 2.2 MiB | 2004 | 否 | 勉强可用 |
| 2200 行（超限） | 11.04 – 19.12 s | 2.2 MiB | 2004 | **是，truncated=1** | 明确报警，不假装完整 |

逐行同源抽检：500 / 2000 / 2200 三档各抽 2 行，`data_sha256` 与 LS 正本逐一相等。

**必须正视的规模结论**：
- 2000 行单次约 10 秒；超限时仍要读全量（2200 行要翻 22 页），耗时近 20 秒；
- 前端 60 秒轮询、多人同时在线时，等于每 60 秒对 LS 发起 N 次全量翻页；
- 这是当前架构的硬边界，单项目超过 2000 行或人多时必须改成
  「先取指纹、变了才按需取行」或 LS 侧增量接口。**不要对外宣称可以无限扩容。**

### 6.2 服务器是 Windows 时（本次新增）

**先说死活口**：Docker Desktop **不支持 Windows Server**（Docker 官方文档明说，
订阅协议也只允许装在个人电脑/开发工作站）。Windows 上跑 Linux 容器（现有 compose 的
镜像全是 Linux）**只有一条路**：WSL 2 里装 Docker Engine。而 WSL 2 需要嵌套虚拟化。

所以第一步不是安装，是判定：

```powershell
cd windows-docker
.\check-host.ps1 -OutFile D:\Forge\host-check.txt
```

| 结论 | 退出码 | 走哪条 |
|---|---|---|
| `READY` | 0 | 已有 Docker，直接 `forge-stack.ps1 -Action start` |
| `INSTALLABLE` | 2 | 跑 `install-docker-wsl.ps1`（可能需重启一次） |
| `BLOCKED` | 1 | **别硬装**，改走 `windows\install.ps1`（裸机：计划任务 + 本机 PostgreSQL + LS venv） |

判定依据：`HypervisorPresent` 是否为真、build 是否 ≥ 20348（Server 2022+）、
80/443/8100/8300 是否被占用。**低价云主机的 Windows 实例大多没有 VT 透传，
`check-host.ps1` 会在装任何东西之前就把这件事说清楚**，省得装到一半卡死。

新增的 5 个脚本（全部纯 ASCII、无 BOM，避免 PowerShell 5.1 按 GBK 解码导致语法失败）：

| 脚本 | 作用 |
|---|---|
| `check-host.ps1` | 只读检测，输出三态结论 + 可存档报告 |
| `install-docker-wsl.ps1` | 启用 WSL/VM 平台、装发行版、装 docker-ce + compose、写 daemon.json 与 systemd |
| `forge-stack.ps1` | start/stop/restart/status/logs/pull/update/backup/smoke/env/shell |
| `sync-portproxy.ps1` | 把 WSL 的端口发布到 Windows 网卡（**WSL 的 IP 每次重启都变**，不重写就外网打不开） |
| `register-autostart.ps1` | 开机自启计划任务，每 5 分钟幂等补拉一次；必须用「注册 WSL 的那个账户」跑 |

本机验证到哪一步：脚本语法（`Parser::ParseFile` 全 0 错误）、编码（非 ASCII 字节 0）、
`check-host.ps1` 实际运行、`forge-stack.ps1` 两条错误分支（目录不对 / WSL 不可用）、
部署包纳入 + 静态核对。**没有验证的是「真实 Server 2022 上从零到 smoke 全绿」——
这台开发机没有 Docker 且 `wsl.exe` 被本机安全策略拦截，跑不了。**

## 八、一句话回答「明天能上线吗」

**代码和交付包可以带过去，但不能指望「解包 → install → 完事」。**
必须先在一台干净 Linux 上把 `install.sh` + `smoke.sh` 跑通，把上面 4 项人工验收做完，
再决定是否开放公网。最可能卡住的不是业务逻辑，而是镜像构建、容器内迁移和 HTTPS 这三件事。
