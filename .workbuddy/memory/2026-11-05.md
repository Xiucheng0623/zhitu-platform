## SSO 搁置 + 自有账号体系稳定性加固（同日，第六轮）

### 用 `tests/diagnose_stability.py` 体检出来的三个真问题

1. **scrypt 在事件循环里同步执行 —— 一个人登录，全公司卡住**
   - 现象：8 个并发登录整批 6853 ms（= 串行），期间一个无关的
     `/healthz` 被阻塞 **6644 ms**。
   - 根因：`hashlib.scrypt` 是同步 CPU 密集型调用（N=2^14），直接在
     async 路由里跑就按住整个 loop。
   - 修法：新增 `verify_password_async` / `hash_password_async`
     （`asyncio.to_thread`），改掉 login / change-password / register /
     reset-password / sso_link 全部调用点。`change_password` 重构成三段
     （取哈希 → 线程池算 → 写回），中间不持有数据库连接。
   - 效果：并发 8 次登录 6853→931 ms，风暴期间 healthz 6644→42 ms。

2. **`/healthz?deep=1` 被外部系统拖死（2.1 秒）**
   - 根因：深度检查直连 Label Studio，未启动时连接失败 × 2 次往返。
     监控每秒打一次就等于自己 DoS 自己。
   - 修法：`clients.py` 给 ping 加 **1 秒硬预算（asyncio.wait_for）+
     15 秒结果缓存**。现在首次 ≤1.2s、之后 10 ms。
   - 配套：README 写清 `/healthz`（10ms，监控用）与 `?deep=1`（人工排查用）
     的区别；Windows 部署排错表加了一条。

3. **改密白算一次 scrypt**
   - "新密码不能与原密码相同"原来用哈希比对 —— 但 scrypt 每次随机 salt，
     哈希必然不同，这个判断永远为 False，还白跑一次 100~900 ms。
   - 改成直接比字符串。

### 一个容易误判的环境事实（重要）
本机（i9-14900HX 大小核 + "平衡"电源方案）单次 scrypt 要 **~850 ms**，
而独立进程里只要 **114 ms**。把后端进程亲和性绑到 CPU 0-15（P-core）后
降到 **455 ms**。结论：**这是 CPU 调度特性，不是代码问题**；
服务器上单次登录应在 100~300 ms。诊断脚本因此把延迟预算分成两档
（含 scrypt 接口 3 s / 普通接口 800 ms），不然永远测不出真问题。
