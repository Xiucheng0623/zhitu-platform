## 第四轮：用户要「在 Windows 服务器上部署 Docker」

### 事实核查（别再说错）
- **Docker Desktop 官方不支持 Windows Server**（docs 明写 only Windows 10/11 client；
  订阅协议限定个人电脑/开发工作站）。服务器上装 Desktop 既不合规也不受支持。
- Windows Server 上跑 Linux 容器（本项目镜像全是 Linux）唯一路径 = **WSL 2 + Docker Engine**。
  Server 2022(20348+)/2025 支持 WSL2；**Server 2019 只有 WSL1，跑不了 Docker**。
- WSL2 需要**嵌套虚拟化**。低价云 Windows 主机普遍不给 VT 透传 → 装了也起不来。
  所以流程必须是「先判定、再安装」。

### 交付：`platform/deploy/windows-docker/`（5 个脚本 + 中文 README）
| 文件 | 作用 |
|---|---|
| `check-host.ps1` | 只读检测，三态结论 READY(0)/INSTALLABLE(2)/BLOCKED(1)，可存报告 |
| `install-docker-wsl.ps1` | 启 WSL/VMP 功能、装发行版、docker-ce+compose、daemon.json、systemd、.wslconfig |
| `forge-stack.ps1` | start/stop/restart/status/logs/pull/update/backup/smoke/env/shell |
| `sync-portproxy.ps1` | WSL IP → Windows 网卡 portproxy（**IP 每次重启都变，必须每次重写**）+ 防火墙 |
| `register-autostart.ps1` | 计划任务自启，每 5 分钟幂等补拉；必须用注册 WSL 的同一账户（SYSTEM 看不到 per-user distro） |

### 本机验证到哪一步
- 5 个 ps1 全部：`Parser::ParseFile` 0 错误、非 ASCII 字节 0、无 BOM（PS 5.1 按 GBK 解码的坑）。
- `check-host.ps1` 实跑：本机 Win11 家庭版 build 26200 / HypervisorPresent=True → INSTALLABLE；
  WSL 部分因安全策略拦 `wsl.exe` 报「拒绝访问」。
- `forge-stack.ps1` 两条错误分支实测：目录不对 → 友好失败；WSL 被拦 → 提示 access denied /
  distribution not found 而不是抛栈。（原来 `$ErrorActionPreference=Stop` 会把
  NativeCommandFailed 变成终止错误，已加 `Invoke-WslRaw` / `Invoke-Native` 包住。）
- **未验证**：真实 Server 2022 上从零到 smoke 全绿。本机无 Docker 且 `wsl.exe` 被策略拦，做不了。

### 打包与核对
- `make_package.py` 现在把 `windows/` 与 `windows-docker/` 打进同一个包（0.7 MB），
  理由：服务器是 Windows，一个包带两条落地路径比维护两个包更不易错。
- `check_package.py` 新增：6 个 Windows 文件必检 + 内容断言 + **第 4 节「.ps1 编码」检查**
  （无 BOM 时必须纯 ASCII，否则 5.1 下语法直接失败）。
- `deploy/README.md` 顶部加醒目段落「服务器是 Windows？先读这一段」，写明 Desktop 不支持
  Server、两条路、必须先跑 check-host.ps1；check_package 有对应断言防误删。
- `check_package.py` / `probe_package_health.py` 全绿。

### 结论口径
- 能在 Windows 服务器上跑，但**不是装 Docker Desktop**，是 WSL2 里装 Engine；
- 先跑 `check-host.ps1`，`BLOCKED` 就老实走裸机 `windows/install.ps1`；
- 本机（开发机）装不了 Docker，是安全策略拦 `wsl.exe` 的环境限制，不是脚本问题。

- 交付形态是「EXE + payload/ 同目录」而不是单个巨型 exe（镜像 2–3 GB，FAT32 放不下、升版要重打整包）。

  否则 build-only 服务没有稳定镜像名，`docker save` 无从引用（离线交付的硬前提）。`make_payload` 落盘时把 tag 定死。
- 安装 `compose up -d --no-build`：离线环境 build 必然失败且失败点很深（3 分钟后 pip 超时）。
- 重装不换密钥（已有完整 .env 就保留），换钥匙会把所有人踢下线。
- 打包解释器必须**带 tkinter**：用 `Python311`（Tk 8.6）；托管解释器与 LS venv 都没有 tkinter。
- .NET Framework 的 C# 编译器被本机安全策略列为编译型程序拦截、`dotnet` 也没装 → C#/WinForms 路线不可行，选 Python + tkinter。

**本机踩到的四个真 bug（都已修）**：
1. 高 DPI 下窗口被系统位图拉伸（截图坐标都对不上）→ `setup_dpi()` 开感知 + 字号/行高/窗口尺寸按 `dpi/96` 缩放。
2. 子线程里 `self._auto.get()` / `root.after` → `RuntimeError: main thread is not in main loop`，
   改为只往队列写，刷新在主线程续期。
3. 底栏按钮塞不下时 pack 把最后 pack 的控件压成 0 宽（启动/停止直接"消失"）→ 底栏改两行。
4. `--noconsole` 打出的 exe 里 print 没地方看 → `cli_sink()` 同时写 `%LOCALAPPDATA%\Zhitu\logs\cli-*.log`。
   另加 `fix_console()`（输出流 UTF-8 + 代码页 65001），cmd/管道/日志三种通道都不乱码。

**结论变化**：本机宿主判定从误判 `BLOCKED` 改成 `INSTALLABLE`——
没有 wsl.exe 只是"功能没启用"，是可安装状态；`BLOCKED` 只留给系统版本过低/虚拟化缺失。

## 其它收尾
- 部署包 0.7 MB 全绿（新增 windows-client 源码 + compose 固定镜像名断言）；`check_package.py` 修掉
  「二进制资产永远判缺失」的缺陷（存在性判断从 blob 扩到 present）。
- 本机三服务重启：LS 8080 / 编排层 8300 / 前端 9121（`/d/forge-ls/env.local`）。

## 联网安装改造 + 两个致命缺口（2026-11-08 晚）

用户前提变了：服务器是 **Win11 + 能出外网**，所以客户端加了「联网构建」模式。

### 改造内容
- 安装程序从 10 步变 11 步：新增 **第 10 步「LS 长期凭证」**（登录 LS 取 refresh
  token 写回 .env 并重启编排层）。不做这步 = 服务全绿但标注完平台数字不动。
- 界面加「自动 / 联网构建 / 离线镜像」分段按钮 + 服务器地址输入框；
  `--auto` 支持 `--online` / `--offline` / `--host-ip`。
- 端口全部改正：平台 **:80**（caddy）、LS **:8100**；旧的 8100/8080 是错的。
  少改了会一直误报「平台不可达」，把人引向错误排查。
- 监控台新增「补凭证」按钮；「启动」按本地是否已有 zhitu/* 镜像决定带不带
  `--no-build`；「修复网络」改用 `HOST_PORTS`（80/8100），之前遍历 STACK_PORTS
  会重复映射 80 又漏掉 8100。
- `make_payload.py` 现在铺 `payload/compose/{caddy,docker,src/**}`，约 1.44 MB / 98 文件。

### 两个真缺口（离线路径也中招，只是没人装过所以没暴露）
1. **`compose` 挂载 `./caddy/Caddyfile`，官方 caddy 镜像不带它**。Linux 那边靠
   `install.sh` 从 `Caddyfile.ip` 复制生成；Windows 客户端原来只拷 compose+迁移 →
   caddy 一直重启、80 端口整条入口没了。现在载荷里直接放好 `caddy/Caddyfile`。
2. **联网构建需要整棵源码树**。`build.context: .` + `dockerfile: docker/xxx.Dockerfile`
   + `COPY src/web/`、`src/orchestrator/`、`src/labelstudio/brand`。载荷原来只有
   compose+迁移 → 现场 build 第一步就报找不到 Dockerfile。现在按 Dockerfile 期望的
   相对路径原样铺好，2 MB 以内搞定（对比 2-3 GB 镜像）。

### 新增 `verify_payload.py`（不需要 Docker/WSL 的交付前校验）
33 项：载荷结构 → payload/compose 落盘逐字节一致 → compose 里每个
`dockerfile:`/`context:`/bind mount 能否解析 → .env 必填与公开地址 →
两种方式各自可行 → GUI 与 `--auto` 步骤表不漂移。**验不了**镜像拉不拉得到 /
build 会不会超时 / 容器能否起来。

### 本机环境新坑
- **Bash heredoc 里反斜杠被吞成 `/`**：`\s` 变 `/s`、`\.` 变 `/.`，正则静默失效，
  我因此得到过一次「dockerfile 引用 0 处、未解析引用 0」的假通过。涉及正则/转义的
  脚本一律用 Write 工具落盘再执行，别走 heredoc 内联。
- `SendMessage`/工具调用里 `wsl.exe` 被安全策略拦，`--status` 的 WSL 一栏必然是「不可用」。
- `_shot.py` 截图两个坑：① Windows 把未激活窗口放 (-32000,-32000)，
  按 winfo_rootx 抓是黑图；② 用 `update()` 泵事件时窗口可能没真映射，抓到的是
  编辑器自己的窗口。改法：`after()+mainloop()` 走正常事件循环 +
  `PrintWindow(PW_RENDERFULLCONTENT)` 按 HWND 取内容（对遮挡免疫）；
  改过 geometry 后 `winfo_id()` 可能指向刚重建的小窗口（实测 237x39），要沿
  `GetParent` 往上取「尺寸最接近 Tk 自报尺寸」的那个 HWND。
- `Text` 默认按 80 字符算请求宽度（≈1040px），把窗口顶到 1200+ 逻辑像素；
  日志框必须 `width=1` 交给 pack 决定。
- `ttk.Radiobutton` 在 clam 主题下三个指示圆圈长得几乎一样（分不出选中谁），
  `ttk.Checkbutton` 被画成 10px 小叉 → 结构性选择一律换成**文字化按钮**。
- pack 是按打包顺序分配空间的，后 pack 的先被压成 0；底栏必须
  `pack(side="bottom", before=<第一个可伸缩区>)`，否则窗口一矮按钮就消失。
- `client.json` 会被测试污染（假 IP 写进用户真实配置，监控台之后一直显示假地址）
  → 新增 `ZHITU_CONFIG_DIR` 环境变量隔离。

### 当前状态
`verify_payload.py` 33/33、`check_package.py` 全绿、两个 EXE 重打（各 11.4 MB）、
发布目录 25 MB、部署包 0.7 MB。**未在真实 Win11 上跑过从零到全绿**，
镜像拉取/npm ci/pip install 的真实耗时与失败率未知。

## 原生 Windows 路线（`platform/deploy/windows-native/`）—— 本轮主线
用户明确「服务器是 WINDOWS」「我需要能一键安装」，我定的是**纯原生路线**：
PostgreSQL for Windows + 两个 Python venv（编排层 / Label Studio）+ caddy.exe +
三个计划任务。不碰 Docker、不碰 WSL、不需要嵌套虚拟化。

### 验证到哪一步（都是本机真跑出来的）
- **PG 官方源全链路 OK**：解压 → `initdb` → `pg_ctl start` → 建库 → 建角色 →
  10 个迁移全过 → **32 张表** → `forge_app` 能登录。
- **PG 备用源全链路 OK**：`full` 工具集缺失（没有 psql/pg_dump）时，SQL 由 venv 里的
  psycopg 逐条执行，同样 10 个迁移全过。
- **LS 1.23.2 在 Windows + Python 3.11 pip 装成**，品牌补丁 `changed=27 failed=0`。
- `verify_payload.py` **58/58**；两个原生 EXE 各 11.4 MB；发布目录 25 MB；
  `--selftest` / `--status` 从 release/ 实跑；监控台与安装向导截图核对过。

### 这一轮踩到的真坑（写进代码了，别改回去）
1. **`pg_ctl start` 不能用 `subprocess.run(capture_output=True)`**：postgres 继承父进程
   的 stdout/stderr 管道，pg_ctl 退出后管道仍被它持有 → run() 一直等 EOF，表现是
   "启动时卡死"，超时杀掉 pg_ctl 也没用。对策：`zn_common.run_daemon()`（DEVNULL）。
2. **EDB 官方 zip 只有一家在发**：tuna/nju/bfsu/aliyun/huawei/tencent 的
   `postgresql/binary/` 全是 404（实测）。替代源 = Maven Central 上 io.zonky.test 的
   `embedded-postgres-binaries-windows-amd64-17.2.0.jar`（23 MB，**只有服务端**）。
   于是安装程序必须能在没有 psql 的情况下建库/迁移 → `sql_split()` + psycopg 子进程。
3. **`initdb` 在本机要 60–90 秒**，不是卡住。40 秒超时会误判成失败。
4. **数表要连 `forge` 库**：`_db()` 默认连 postgres 库，在那儿数永远是 0。
5. **监控台不能用端口判断自己的数据库**：本机 5432 上是另一个 PostgreSQL，旧逻辑
   误报"在监听"。改成先问 `Get-Service ZhituPostgreSQL`（Status 恒为英文，
   `sc query` 的状态文字会被本地化）再看端口。
6. 步骤表原来 GUI 与 `--auto` 各一份 → 收敛成 `STEP_SPEC` + `step_list()`，
   `verify_payload.py` 断言两边同源。
7. 建库必须在编排层 venv 之后（没有 psql 时 SQL 靠它的 psycopg 执行），步骤顺序
   改成 03 PG → 04 编排层 → 05 建库迁移。

## 交付形态改成「一个 zip」（2026-11-09 用户追问「不能就发一个包吗」）
- 之前是「两个 exe + payload/ 目录」，客户要整目录拷、漏一个文件就装不上。
- 现在：`build_native.py` 用 PyInstaller `--add-data <payload>;payload` 把载荷塞进
  安装程序 exe（11.4 → 12.1 MB）；`zn_common.payload_dir()` 在 frozen 时优先读
  `sys._MEIPASS/payload`，读不到再退回 exe 同层 payload/（兼容老形态）。
- 新增 `make_release.py`：收 `release/`（两个 exe + 安装说明.txt）+ 打
  `deploy/dist/智途-Windows原生-<日期>.zip`（23 MB）。**发这一个文件就够。**
- 内嵌后 `payload/cache` 是只读的 → 新增 `zn_common.cache_dirs()`：
  认 `exe旁\cache\`、`exe旁\payload\cache\`、`载荷内\cache\`（离线部署把 PG/caddy
  包放 exe 旁边即可）。selftest 也改成扫这三处。
- `verify_payload.py` 默认**不再重建** payload（改 `--build` 才重建），并新增

  （否则说明载荷没内嵌进去）。现在 **60 项**。
- 实测：空目录只放一个安装程序 exe → `--selftest` 六项载荷全"有"，
  `payload_dir` 指向 `_MEI...\payload`；exe 旁放 `cache\*.jar` 能识别。
