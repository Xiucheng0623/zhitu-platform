## 「点自定义快捷键一直转圈」的完整答案（12:15）

### 三个独立的真因，别混成一个
1. **白屏 14 秒**：`/api/jwt/settings` 被 `forge_sso.py` 的 `API_TOKEN_RE` 当成"签发接口凭证"拦成 403
   （body 是 `{"detail":"当前账号无权签发接口凭证。"}`）。账号页拿不到设置 → 空壳。
   → 新增 `API_SETTINGS_READ_RE`，只放行该路径的 `GET/HEAD`；**POST 仍然拦**（它是组织级写入）。
2. **遮罩迟迟不撤**：`workbench-shell.html.fragment` 的 `appReady()` 只认 `.lsf-main-view / .lsf-datamanager / ...`，
   账号页 `/user/account/*` 永不匹配 → 只能等 12 秒兜底。
   → 加 `LIGHT_PAGES = /^\/user\/account(\/|$)|^\/user\/login/` 分支，判 `.app-wrapper/#root` 有子节点即可。
3. **"没法用"**：`window.Htx` 在 LS 1.23.2 不存在，增强层保存/提交/校验/复用全静默失效。
   → `H()` 两级兜底 `window.LabelStudio.instances.values().next().value.store`。

### 键位页的真实交互（这次终于摸清，之前猜错两轮）

```
行 = div[flex items-center py-3 border-b]
  ├ 开关 / 操作名 + 说明

```

  这就是上一轮"点 Apply 抓不到 PATCH"的原因，不是功能坏了。

## 「个人访问令牌」是什么 / 为什么封掉（13:40）

### 它是什么
Label Studio 原生的 **Personal Access Token**：一个长期 API 密钥，拿 `Authorization: Bearer <token>`
就能在脚本里直连 LS 的 REST API，不用走浏览器登录。LS 官方文档所有 API 示例都用它。
CE 里默认**永不过期**（`Enable legacy access tokens, these do not expire`），这才是最危险的点。

### 为什么必须封
平台调 LS 用的是**组织级 refresh token 服务账号**（`FORGE_LS_REFRESH_TOKEN`），跟个人令牌是两套。
标注员一旦签出个人令牌，就绕开了两层边界：
1. 平台 SSO（不需要经过平台登录）
2. 项目授权 / RLS（`/api/projects` 直接拉全部项目、全部任务数据）
服务端早已封死签发面：`forge_sso.API_TOKEN_RE = ^/api/(token|jwt)|^/api/current-user/(token|reset-token)`；
标注员 `_guard` → 403「当前账号无权签发接口凭证。」，甲方设计会话 `_guard_designer` → 404。
**只在 `API_SETTINGS_READ_RE` 放行 `/api/jwt/settings` 的 GET/HEAD**（只读两个布尔值，POST 仍拦）。

### 实测（本机 LS 1.23.2）
- `GET /api/current-user/token` → **403**，body `{"detail":"当前账号无权签发接口凭证。"}`
- `POST` 同上 403；页面上「创建新令牌」**disabled**，tooltip「你只能保留一个有效令牌」
- 页面正文停在 `Authenticate with our API... See` + `loading...` —— 因为列表接口 403 拿不到
- 路由真名是 **`/user/account/personal-access-token`**（`/user/account/token` 会被重定向到 personal-info）

### 改了什么
`ls-runtime-brand.js` 新增 `dropPatEntry()`：按 `a[href*="/user/account/personal-access-token"]`
摘掉整个 `<li>`，文案兜底 `/^(个人访问令牌|Personal Access Tokens?|API Tokens?)$/`（≤12 字，不收裸词，
避免误摘标注界面里叫「令牌」的选项按钮）。服务端中间件仍是唯一安全边界，前端只是不让人点进死页面。
**不做直连 URL 的说明条**：实测 LS 对这条 URL 的直连会渲染「个人信息」页（URL 不变内容换），
固定定位说明条会盖住顶部标题栏和主题开关，比不提示更糟。入口已摘，这条路径实际走不到。
`zh-cn.js` 补 `"Authenticate with our API using your personal access token. See"`（原词条带 `Docs`，
页面里 Docs 是独立节点，整句匹配不上）。

验证脚本 `platform/web/tools/.tmp/verify_pat_hidden.py`：菜单项 4 个（无令牌项）、直连 URL 无残留、
标题栏未被遮挡 —— 全部 PASS。`verify_brand.py` RESULT OK。
交付包重打：payload 73 文件 → exe 12.1/11.4 MB → `verify_payload` 60/60 → zip 23.0 MB。

### 两个硬阻塞 + 一个提醒
1. **内存差 4.7 倍**：README 要求 4 核 8 GB。预算（估算）：运行期 7 个容器 ≈ 1.2–1.6 GB
   （LS 最胖 0.4–0.7 G，PG×2 ≈ 0.3 G，编排层 0.2 G，minio 0.15 G，caddy/web 0.05 G，系统+docker 0.3 G）；
   构建期峰值 2.5–3 GB（vite 打包 + pip 装 LS 同时跑）。**不加 swap 必然在 build 阶段 exit 137**。
   → 6 GB swap + swappiness=10 可以装、可以演示；多人同时标注会因换页明显变卡，长期要升到 4C8G。
2. **网段与 Docker 默认池直接冲突**：宿主 172.17.0.4/20 → 网段 **172.17.0.0/20**，
   而 Docker 给 docker0 的默认地址就是 **172.17.0.1/16** —— 不只是网段重叠，**IP 很可能就是 VPC 网关**。
   → 装完 docker 立刻钉死 `bip=10.211.0.1/24` + `default-address-pools=10.212.0.0/16 size 24`，

3. 控制台放行 80/443/8100（CVM 叫安全组，轻量叫防火墙）；2 核构建要 30–60 分钟，SSH 一断就中断 → 放 tmux。

## 真机第一阻断：第 03 步 initdb「Permission denied」（已修）

用户截图：`initdb: 错误: 无法改变目录 "C:/Zhitu/data/pgdata" 的权限: Permission denied`，
前面还有一句 `属于此数据库系统的文件宿主为用户 "Administrator"`（这句是**正常提示**，不是错误）。

**根因（不是权限问题，是「非空目录」问题）**：`pg_initdb` 只判 `PG_VERSION`：
有就跳过、没有就 `mkdir(exist_ok=True)` 然后在**原目录**上跑 initdb。
上一次 initdb 中途失败 → 目录里留下残骸、`PG_VERSION` 没写出来 → 下次判定「没装过」→
在非空目录上跑 initdb → initdb 先走 `fixing permissions on existing directory`（改 ACL）→
Windows 上被拒 → 报同一句。**每重跑一次都是同一处，永远过不去。**

三处修改（`zn_common.py`）：
1. `pg_data_state()` 四态：`cluster`（有 PG_VERSION，**绝不碰**）/ `leftover`（非空无
   PG_VERSION = 残骸）/ `empty` / `absent`。initdb 成功第一件实事就是写 PG_VERSION，
   所以这个判据是可靠的。
2. `force_rmtree()`：只读属性 `os.chmod(S_IWRITE)` + `taskkill postgres.exe` + `rmdir /S /Q` 兜底，
   三轮重试。**清理前先 `sc.exe stop ZhituPostgreSQL`** —— 只 kill 进程不够，SCM 会按恢复策略
   把它拉回来，变成「删一半又报 Permission denied」。
3. **不再预先 mkdir 数据目录**，让 initdb 自己创建（新建走继承权限，不需要改 ACL）。
   空目录也先 rmdir 掉。失败再清空重试一次（杀软实时扫描会偶发 chmod 失败）。
4. 失败文案带 4 行可粘贴命令（sc stop / taskkill / takeown / Remove-Item），GUI 直接可读。

**顺手挖出的第二个重跑 bug**：`step_postgres` 用 `task_exists(PG_SERVICE)` 判自己的库，
但 PG 是 `pg_ctl register` 注册的 **SCM 服务**，schtasks 永远查不到 →
① 自己的库占着 5432 却被判成「别人占用」→ 自动换 5433，配置写 5433、库在 5432，装完连不上；
② 判「服务不存在」→ 再 register 一次 → `service already exists` 失败。
→ 新增 `service_exists()`（`sc.exe query` 只看**退出码**，不解析本地化文本），两处都换掉。

验证（本机 `_t_initdb.py`，5 场景全过，测完已删）：leftover 清理后重建成功 / empty 成功 /
**cluster 跳过且原数据文件不动** / 首次失败自动重试成功 / 两次失败文案含 takeown+Remove-Item。
`verify_payload` 60/60，`check_package --source` 全绿。
新包 `智途-Windows原生-20261109.zip` 24,180,517 B，SHA256 44d737b8…52d223。

### 核心手法（关键，别忘）
1. **embeddable Python 3.13.7 做底座 + 把 venv 的 site-packages 直接并入**
   - 现成的 `/d/forge-ls/venv` 是 py3.13.14 + LS 1.23.2，直接复制过来当运行时
   - **venv 不能重定位**：`python313._pth` 存在时 Python 忽略 `pyvenv.cfg`，`sys.prefix`
     永远指向 exe 所在目录 → 改 pyvenv.cfg 无效（实测过，别浪费时间）
   - 正解：把 `Lib/site-packages` 移进 embeddable 目录，`_pth` 写
     `python313.zip / . / Lib/site-packages / import site`
   - 这样 `python.exe -c "import label_studio"` 直接可用，**不需要 pip 装 20 分钟**
2. **两份运行时**（不合并）：py-ls 装 LS 全依赖，py-orch 只有 116 MB。
   合并会撞 pyjwt 版本（label-studio-sdk 要 <2.14，编排层要 >=2.9 但装了 2.15）。
3. **PG 只解压 bin/lib/share**，跳过 pgAdmin 4 + StackBuilder（21302 个文件）→ 130 MB 而不是 500 MB。
4. **caddy 可缺**：`stage_runtime` 里 caddy 缺席不算致命，第 09 步自己下 45 MB。

### 这个环境的四个坑（都很浪费时间）
1. **Git Bash 会把命令行/heredoc 里的 `\n` 变成 `/n`**（MSYS 路径转换）。写脚本时

2. **Write / Edit 工具在本项目会报 `sandbox.backup.modify_backup` 超时**，
